# 招聘核心引擎设计

## 目标

在现有 `Job`（岗位 JD）之上补齐可运营的招聘流程：岗位状态、负责人、HC、可版本化流程、候选人应聘记录和人工阶段流转。候选人收藏是独立的轻量标记，不能替代应聘记录。

## 范围与边界

- 扩展现有 `Job`，不新建第二套岗位模型。
- 默认流程为：待筛选 → 初筛 → 面试 → 复试 → Offer → 已录用 / 已淘汰。
- AI 可以生成说明或建议，但不得创建应聘记录、推进阶段、淘汰或录用候选人。
- 招聘流程中的每一次变更都由已登录的工作区成员主动发起并保留历史。

## 数据模型

`Job` 增加招聘状态（草稿、招聘中、暂停、已关闭）、部门、负责人、HC 和当前适用于未来应聘记录的流程版本。

一个工作区可维护多个 `RecruitingWorkflow`。每次修改都会创建新的 `RecruitingWorkflowVersion` 和完整的阶段集合，已发布版本永不原地改写。每个版本至少有一个进行中阶段，并且恰好一个“已录用”和一个“已淘汰”结果阶段。

`JobApplication` 是候选人 × 岗位的独立记录，固定保存当时的：

- 候选人和启用简历引用；
- 简历事实快照和事实版本；
- 已确认 JD 版本；
- 流程版本和当前阶段快照。

同一候选人在同一岗位同一轮次只有一条记录。终态后可由招聘人员重新加入岗位，系统创建下一轮记录，不覆盖旧轮次。`JobApplicationStageTransition` 只追加，保存操作人、前后阶段、备注和状态版本。

## 人工流转与并发

进行中的记录可以手工推进、退回、淘汰；只有处于最后一个进行中阶段时才能录用。浏览器提交当前 `state_version`，服务端执行带版本条件的更新；版本不匹配时返回冲突，不覆盖另一位招聘人员的操作。岗位不是“招聘中”时，不能新增或继续流转。

## 租户与隐私

流程、阶段、岗位、应聘记录和流转历史均属于当前工作区，并受 ORM 工作区范围与复合外键双重约束。所有读取均通过当前工作区和存活候选人/简历根记录查询；跨工作区 ID 与不存在的 ID 均返回同样的未找到结果。

候选人或简历删除后，应聘记录不会继续在正常工作台出现。进入物理清理期后，先删除该应聘记录和其流转历史，再删除关联事实快照与候选人数据，避免保留可关联的个人资料。

## 交互

- “职位管理”展示岗位列表、招聘设置、流程版本和按阶段分组的候选人。
- 新建岗位仍跳转现有 JD 工作台；创建/发布 JD 后自动初始化默认流程和负责人。
- 候选人详情新增“应聘记录”页签，可由招聘人员显式加入开放岗位并查看历史。
- 终态操作需要明确人工确认；界面不提供 AI 自动决策按钮。

## 迁移与验证

迁移为已有普通岗位按工作区创建并绑定已发布的默认流程，旧岗位保持“招聘中”。验证覆盖：岗位/简历快照、流程新版本只影响后续应聘记录、阶段并发冲突、跨工作区访问、候选人删除与物理清理，以及 SQLite 升级和 PostgreSQL DDL 兼容性。
